# 制度三：独立审查与验收（Independent Acceptance）

## 1. 核心原则

实现者不能单独证明自己的实现正确。开发自检、代码审查、QA 验证和最终批准是不同责任。

## 2. 三道关卡

### Gate 1：Developer 自检

必须完成：
- 检查工作区和最终 diff
- 运行相关构建、单元测试、静态检查
- 更新必要测试
- 检查秘密、无关文件和意外变更
- 提交 Handoff Report

结果：`IMPLEMENTED`。Developer 不得将自己任务标记为 `DONE`。

### Gate 2A：独立代码审查

Reviewer 检查：
- 正确性、边界条件、错误处理
- 架构和决策合规
- 安全、隐私、秘密处理
- 数据完整性和兼容性
- 性能与资源使用
- 测试质量和缺失覆盖
- 变更范围和可维护性

结果：
- `APPROVE`
- `REQUEST_CHANGES`
- `BLOCKED`

Reviewer 必须引用文件和行号，描述影响和修复建议。Reviewer 不修改代码。

### Gate 2B：独立 QA

QA 根据验收标准自行设计测试，执行自动化和必要的手动测试。

结果：
- `PASS`
- `FAIL`
- `BLOCKED`
- `NOT RUN`

QA 报告必须列出测试环境、命令、结果、证据、未测项目和风险。

代码审查通过不代表 QA 通过；编译成功不代表运行时行为通过。

### Gate 3：最终验收

主 Agent 汇总证据并提出建议；人类项目负责人按项目权限批准合并/发布。

任务成为 `DONE` 的必要条件：
- 所有强制验收标准通过
- Reviewer 无未解决 P0/P1
- QA 对强制范围给出 PASS
- CI 必需检查通过
- 许可证、安全、数据迁移等专项门禁通过（如适用）
- 交接、审查和 QA 报告已归档
- 所有例外均有明确批准人、理由和到期/复查条件

## 3. 缺陷严重级别

- P0 Critical：安全漏洞、严重数据丢失、系统性故障；立即阻断。
- P1 High：核心功能失败、关键验收不通过、重大兼容性问题；合并前必须修复。
- P2 Medium：非核心缺陷或显著维护风险；通常修复，若延期须记录并批准。
- P3 Low：轻微问题或建议；可进入后续任务。

## 4. 证据标准

有效证据包括：
- CI 运行链接和具体 job 结果
- 实际命令、退出码和测试输出
- 自动化测试报告
- 目标系统实机测试记录
- 可复现步骤、日志、截图或录屏（注意脱敏）
- 性能数据及测试环境基线

无效证据：
- “我检查过了”
- “应该能运行”
- 未执行的测试被标记 PASS
- 仅由实现者口头声称的性能改善
- 没有环境信息的截图或数字

## 5. 权限边界

| 操作 | Developer | Reviewer | QA | 主 Agent | 人类负责人 |
|---|---|---|---|---|---|
| 读取代码 | 允许 | 允许 | 允许 | 允许 | 允许 |
| 修改任务代码 | 允许 | 禁止 | 默认禁止 | 按授权 | 允许 |
| 执行测试 | 允许 | 可选只读检查 | 允许 | 允许 | 允许 |
| 批准自己的 PR | 禁止 | 不适用 | 不适用 | 禁止 | 允许 |
| 合并受保护分支 | 禁止 | 禁止 | 禁止 | 默认需批准 | 允许 |
| 正式发布 | 禁止 | 禁止 | 禁止 | 默认需批准 | 最终批准 |

## 6. 工具与平台保护

OpenCode Agent 权限只是工具调用层面的约束，不是完整安全沙箱。必须同时使用：
- GitHub/Git 平台受保护分支
- 必需 CI 检查
- PR 审查规则
- 最小权限 Token
- 机密信息管理
- 发布审批与签名密钥隔离

对高风险命令（push、merge、force push、reset、clean、删除分支、发布、生产部署）采用拒绝或逐次人工批准策略。

## 7. 例外管理

任何跳过审查、QA 或门禁的行为都必须记录：
- 被跳过的门禁
- 原因和风险
- 影响范围
- 临时缓解措施
- 批准人
- 复查日期

AI 不得自行批准门禁豁免。
