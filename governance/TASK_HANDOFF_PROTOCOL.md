# 制度二：任务分配与交接协议（Task & Handoff Protocol）

## 1. 目标

让任务可分派、可并行、可追踪、可复核，并降低 Agent 上下文不完整、范围漂移和交接遗漏的风险。

## 2. 任务准入条件

任务进入 `READY` 前必须具备：
- 唯一 Task ID
- 明确目标和背景
- 相关 PRD/DECISIONS/架构引用
- 明确的范围和排除项
- 允许修改的文件或目录（如适用）
- 依赖和前置条件
- 可验证的验收标准
- 测试/构建/手动验证要求
- 预期交付物
- 风险和负责人

不满足时保持 `BACKLOG` 或 `BLOCKED`，不得让 Developer 猜测需求。

## 3. 状态定义

| 状态 | 含义 | 进入条件 |
|---|---|---|
| BACKLOG | 尚未准备执行 | 需求尚不完整或未排期 |
| READY | 可执行 | 任务卡完整、依赖满足 |
| IN_PROGRESS | 正在实现 | 已分配 Agent 和工作区 |
| IMPLEMENTED | 实现完成 | Developer 已自检并提交交接 |
| IN_REVIEW | 代码审查中 | Reviewer 已收到明确 diff/base |
| IN_VERIFICATION | QA 验证中 | 审查结果可接受，测试环境可用 |
| BLOCKED | 阻塞 | 依赖、环境、决策或测试条件不满足 |
| CHANGES_REQUESTED | 需要修改 | Review 或 QA 发现必须修复项 |
| DONE | 验收完成 | 审查、QA 和项目门禁全部满足 |
| CANCELLED | 已取消 | 项目负责人确认取消 |

`IMPLEMENTED`、`IN_REVIEW`、`IN_VERIFICATION` 均不等于 `DONE`。

## 4. Agent 分工

- 主 Agent：拆解任务、确认上下文、分配子 Agent、整合结果。
- Architect：为复杂或跨模块任务提供设计和接口建议。
- Developer：一个任务一个明确实现负责人。
- Reviewer：独立审查实际差异。
- QA：独立验证验收标准。
- 人类项目负责人：批准重大决策、风险接受、合并和发布。

## 5. 并行规则

允许并行的前提：
- 任务之间没有未解决的共享接口冲突。
- 每个任务有独立分支和独立 worktree/克隆。
- 修改文件范围尽量不重叠。
- 共享接口先由 Architect 定义并批准。
- 集成任务明确负责解决冲突和运行全量回归。

禁止多个 Agent 同时写入同一工作目录。不要仅依靠“请小心不要冲突”的提示词管理并发。

## 6. 交接要求

Developer 完成后提交：
- 任务 ID、分支、base commit、最终 commit
- 修改文件清单及原因
- 实现摘要和重要技术选择
- 实际执行的命令及结果
- 测试证据
- 未执行的检查及原因
- 已知问题、风险和后续工作
- 是否存在超范围修改
- 对应 Handoff Report

Reviewer 必须拿到明确的 base commit 和 head commit，审查真实差异。
QA 必须拿到验收标准、构建产物/运行环境和测试数据说明。

## 7. 阻塞与升级

以下情况必须停止并向主 Agent/负责人报告：
- 任务与已批准决策冲突
- 需要修改任务范围外的重要文件
- 需要破坏性数据库迁移或用户数据操作
- 需要新增高风险依赖或改变许可证义务
- 测试环境缺失导致关键验收无法完成
- 发现安全、隐私或数据丢失风险
- 与其他 Agent 的接口或文件修改发生冲突

## 8. 交接质量门禁

交接报告缺失、测试结果无证据、Git diff 不清楚或工作区状态不明时，不得进入独立验收。
