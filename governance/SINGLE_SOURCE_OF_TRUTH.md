# 制度一：单一事实来源（Single Source of Truth）

## 1. 目标

确保人类、主 Agent、子 Agent、开发者和审查者基于同一套、可追溯且版本化的项目事实工作，避免需求、决策、架构和任务信息分散或互相矛盾。

## 2. 文档权威层级

| 文档 | 回答的问题 | 维护责任 |
|---|---|---|
| PRD | 产品要解决什么问题、做什么、不做什么 | 产品负责人批准；主 Agent 协助维护 |
| DECISIONS | 哪些决策已批准、为何批准 | 人类项目负责人批准 |
| ARCHITECTURE | 系统如何组织、模块如何协作 | Architect 提案；负责人批准重大变化 |
| API_CONTRACTS | 模块如何通信、数据格式是什么 | 对应模块负责人提案；跨模块变更需审查 |
| DEVELOPMENT_RULES | 如何编码、构建、测试和提交 | 主 Agent 维护；负责人批准规则变更 |
| TASKS | 当前工作项、依赖和状态 | 主 Agent 维护 |
| TEST_STRATEGY | 如何验证系统 | QA 提案；负责人批准关键门禁 |
| CHANGELOG | 已交付版本包含什么 | 发布负责人维护 |

## 3. 单一事实规则

1. 每项重要事实只设置一个权威位置。
2. 其他文档通过链接或引用表达，不复制一份可独立编辑的事实。
3. 对已批准决策使用唯一 ID，例如 `D-IME-001`。
4. 决策至少记录：背景、选项、决定、理由、影响范围、状态、批准人和日期。
5. 未批准方案必须标记 `PROPOSED`，不得写成既定事实。
6. 未验证技术参数必须标记 `VALIDATING`，并列出验证任务。
7. 已废弃决策不得直接删除，应标记 `SUPERSEDED` 并链接替代决策。

## 4. 冲突处理流程

发现冲突时：
1. 暂停受影响的实现。
2. 列出冲突文档、章节、提交版本和实际影响。
3. 判断冲突是过期引用、遗漏更新还是决策本身矛盾。
4. 提出一个最小变更方案及其影响。
5. 等待项目负责人批准。
6. 更新权威文档、引用文档和相关任务卡。
7. 在提交记录中关联决策 ID。

不得由 Agent 自行推断“哪个文档看起来更新”并静默覆盖另一个文档。

## 5. 变更管理

以下变更必须更新 DECISIONS 或架构文档：
- 产品范围、核心用户流程
- 技术栈、进程边界、模块职责
- API、持久化数据格式、配置格式
- 隐私、安全、权限、更新和恢复机制
- 第三方依赖及许可证策略
- 性能目标和发布门禁

小型实现细节不必产生正式 ADR，但应在任务交接中说明。

## 6. 文档版本与状态

推荐状态：
- `DRAFT`：草稿
- `PROPOSED`：待批准
- `ACCEPTED`：已批准
- `VALIDATING`：方向已定，参数待验证
- `DEFERRED`：明确推迟
- `REJECTED`：已否决
- `SUPERSEDED`：被新决策取代

每次修改应通过 Git 记录作者、时间和差异。不要仅依赖聊天记录作为长期权威事实。

## 7. 最小可行文档集

项目早期至少建立：
- `PRD.md`
- `DECISIONS.md`
- `ARCHITECTURE.md`
- `TASKS.md`
- `DEVELOPMENT_RULES.md`
- `TEST_STRATEGY.md`

允许内容逐步完善，但不得把未完成的文档伪装成已确认规范。
