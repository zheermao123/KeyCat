# 给 OpenCode 的首次落地任务

请先阅读本文件和仓库中的 `README.md`、`AGENTS.md`、`opencode.jsonc`、`governance/`、`.opencode/agents/`。

你现在的任务不是立即开发产品功能，而是把这套《OpenCode 多 AI 协同开发标准 V1.0》安全地适配到当前仓库。

## 第一阶段：只审计，不修改

1. 检查当前仓库根目录、分支、HEAD、工作区状态。
2. 检查已有 `AGENTS.md`、`opencode.json` / `opencode.jsonc`、`.opencode/agents/`、commands、skills。
3. 检查现有 PRD、决策记录、架构、任务、测试、CI、PR 模板和 Git 分支保护约定。
4. 检查 `.gitignore`、敏感目录、密钥、生成文件和第三方许可约束。
5. 对照本标准，列出：
   - 可以直接采用的文件
   - 必须合并而不能覆盖的文件
   - 与现有项目规则冲突的内容
   - 当前 OpenCode 版本可能不兼容的配置
   - 需要人类项目负责人决定的事项

输出 `ADOPTION_AUDIT.md`，不要在此阶段修改任何现有项目文件。

## 第二阶段：提出适配方案

提供逐文件变更清单，明确：
- 新增哪些文件
- 修改哪些文件
- 保留哪些现有规则
- 如何合并 Agent 配置和权限
- 如何验证 Reviewer 只读
- 如何确保 Developer、QA、主 Agent 的高风险操作需要审批
- 如何与现有 GitHub PR / CI 流程衔接

不得删除或覆盖用户已有内容。遇到冲突先提出方案，等待项目负责人批准。

## 第三阶段：经批准后实施

只有在项目负责人明确批准后才实施：
1. 合并项目级 `AGENTS.md` 和 OpenCode 配置。
2. 安装或合并四个 Agent 定义。
3. 建立项目权威文档目录和必要占位文件。
4. 建立任务、交接、审查和 QA 报告模板。
5. 建立或更新 PR 模板。
6. 更新项目说明，记录治理体系入口。

所有新增内容必须适配当前仓库真实技术栈、目录和命令，不得照抄示例中的虚构路径或命令。

## 第四阶段：验证

1. 使用当前安装的 OpenCode 版本验证配置是否可加载。
2. 检查 Agent 是否可发现。
3. 验证 Reviewer 不能编辑文件。
4. 验证 QA 不能编辑产品代码。
5. 验证高风险 Shell/Git 操作会被拒绝或要求批准。
6. 验证 Agent 能读取项目权威文档。
7. 运行仓库现有的文档、配置或 CI 检查（如有）。
8. 输出 `ADOPTION_VERIFICATION.md`，记录实际命令、结果和未验证事项。

## 不可逾越的约束

- 不得覆盖未提交改动。
- 不得直接向受保护分支提交。
- 不得擅自 push、merge、release。
- 不得执行破坏性 Git 命令。
- 不得删除现有 Agent 或配置。
- 不得假称已验证权限或配置。
- 不得将示例任务、示例测试命令当作当前项目真实内容。
- 所有重要冲突和决策必须交由项目负责人确认。

最终先向我报告审计结果和适配计划，不要自行进入产品开发。
